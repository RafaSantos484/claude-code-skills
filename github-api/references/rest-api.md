# GitHub REST resource guide

Use `GH_API`, `GH_API_VERSION`, `GH_OWNER`, `GH_REPO`, and `gh_request` from [authentication and transport](authentication-and-transport.md). Every `gh_request` sends `Authorization: Bearer`, `Accept: application/vnd.github+json`, and `X-GitHub-Api-Version` without putting the token in process arguments. It returns an envelope with numeric `status`, selected `headers`, and base64 `body_b64`, including for HTTP errors. Check status before decoding; `gh_json_body` does this for ordinary 2xx JSON responses. Encode user-provided path segments and query values; never concatenate unchecked user text into a URL. The table is a routing guide, not a replacement for the linked endpoint pages. Recheck exact request fields, required permissions, token support, and GHES version at execution time.

| Task | REST route(s) | Typical fine-grained repository permission |
| --- | --- | --- |
| Identity and repository | `GET /user`; `GET /repos/{owner}/{repo}`; installation repository list plus GraphQL `viewer` for known installation tokens | Public metadata or Metadata read; private data still needs repository selection. See [installation-token verification](authentication-and-transport.md#installation-token-verification). |
| Branches, tags, commits | `/repos/{owner}/{repo}/branches`, `/tags`, `/commits`, `/compare/{base}...{head}`; `/git/refs/{ref}` | Contents read; Contents write for branch/ref mutation. |
| Files and Git objects | `/contents/{path}`, `/git/blobs`, `/git/trees`, `/git/commits`, `/git/refs` | Contents read/write; changing `.github/workflows` can also require Workflows write. See [content guide](repository-content.md). |
| Issues and comments | `/issues`, `/issues/{number}`, `/issues/{number}/comments`; `/labels`, `/milestones`, `/assignees` | Issues read/write for issue operations; check the exact comment, label, milestone, and assignee endpoint, since alternative permission sets can apply. |
| Pull requests | `/pulls`, `/pulls/{number}`, `/pulls/{number}/files`, `/commits`, `/reviews`, `/requested_reviewers`, `/comments`, `/merge`, `/update-branch` | Pull requests read/write. Merge/update can also be restricted by branch rules and repository role. |
| Releases | `/releases`, `/releases/{id}`, `/releases/tags/{tag}`, `/releases/assets/{id}` | Contents read/write by operation. Publishing or deleting a release is elevated if it affects distribution. |
| Checks and statuses | `/commits/{ref}/check-runs`, `/check-runs/{id}`; `/commits/{ref}/status`, `/statuses/{sha}` | Checks read; Commit statuses read/write. Check-run creation is a GitHub App capability, not a generic PAT operation. |
| Actions | `/actions/workflows`, `/actions/workflows/{id}`, `/actions/workflows/{id}/dispatches`, `/actions/runs`, `/actions/runs/{id}`, `/actions/runs/{id}/jobs`, `/actions/runs/{id}/logs`, `/actions/runs/{id}/rerun`, `/actions/runs/{id}/cancel`, `/actions/artifacts`, `/actions/artifacts/{id}/zip` | Actions read/write according to endpoint. Workflow dispatch requires Actions write. |

## REST behavior

- GitHub.com base is `https://api.github.com`; Enterprise Server uses `https://HOST/api/v3`. Use the version supported by that host, never a GitHub.com version by assumption. For Cloud data residency, use the documented API host corresponding to the web host.
- Most list endpoints use `per_page` (usually at most 100), but endpoint limits vary. Use `gh_rest_pages` to follow the envelope's `headers.link` `rel="next"` URL through the same host-checked request path until absent. It emits one envelope per page; on failure it emits only a sanitized class (`transport`, `http`, `invalid_next_url`, `page_limit`, `parse`, or `invalid_input`) and selected HTTP diagnostics on stderr. Do not infer completeness from a short page or `total_count`; if a user asks only for the first N or the helper stops early, label results limited or incomplete and report the failure class. Some list responses wrap results in an object, such as `workflow_runs` or `workflows`.
- A successful authenticated `If-None-Match` request returning envelope `status:304` can save primary rate-limit cost. Keep ETags scoped to the exact token, host, URL, and media type; avoid persisting private response bodies or headers. `GET /rate_limit` can show resource buckets, but response rate-limit headers (the envelope's `rate_remaining` and `rate_reset`) are authoritative. Search has separate rate limits and exposes at most 1,000 results per query; partition a search carefully or state the cap.
- On REST `403`/`429`, inspect the envelope's `retry_after`, `rate_remaining`, and `rate_reset`. Wait until the indicated time; otherwise wait at least one minute for a secondary limit, then use bounded exponential backoff. Make calls serially; pause between mutative calls. Do not automatically replay an uncertain `POST`, `PUT`, `PATCH`, or `DELETE` after a timeout. `409` means conflict and `422` can mean invalid input, a rule rejection, or spam protection; decode only a safe error message, re-read state, and repair intentionally.
- APIs may return `404` for inaccessible private resources. Never interpret it alone as proof of nonexistence. Endpoint-specific permission sets appear in the docs and sometimes `X-Accepted-GitHub-Permissions`. Organization SSO and policy may further restrict a token.

## Issues and pull requests

GitHub's Issues list can include pull requests. Filter entries with `pull_request` or use `/pulls` when the user wants only PRs. Issue and PR numbers are repository-scoped, and a PR is also an issue for shared comments/labels/assignees. Verify assignee eligibility before writing: GitHub documents that some assignee additions are silently ignored when the actor lacks push access. For a general PR comment use `/issues/{number}/comments`; for line comments use `/pulls/{number}/comments` with the documented path/line/side or reply fields. A review is a separate `/pulls/{number}/reviews` resource with `APPROVE`, `REQUEST_CHANGES`, or `COMMENT` event. Requesting reviewers uses `/pulls/{number}/requested_reviewers` and sends notifications. An approval is not a code-quality assessment by itself; use `pr-review` for evidence before posting one if asked to assess code. `/pulls/{number}/files` is capped at 3,000 files even when paginated; label larger results incomplete and use a repository diff strategy if a complete review is needed.

For cross-repository PRs, `head` may need `user:branch`; when both repositories belong to the same organization, `head_repo` may also be required. Verify the actual head repository and branch and the base repository/branch. Never assume `head` is in the base repository. Creation needs write access to the head/source branch. Check `mergeable` after it has been computed, required checks, rulesets, review requirements, and permitted merge methods before merging. The merge endpoint accepts the expected head SHA; use it to avoid merging a newer unreviewed head. Merge queues, stacked PR behavior, update-branch, and auto-merge are distinct operations: check the current endpoint/schema and repo policy, and treat merge/auto-merge as elevated.

An issue creation example, after the target and identity checks and the ordinary-write announcement:

```bash
set -o pipefail
jq -n --arg title "$TITLE" --arg body "$BODY" \
  '{title:$title, body:$body}' |
  gh_request "$GH_API/repos/$GH_OWNER/$GH_REPO/issues" \
    --request POST --header 'Content-Type: application/json' --data-binary @- |
  gh_json_body |
  jq '{number, html_url, state}'
```

The same pattern with `jq --arg`/`--argjson` safely constructs other JSON bodies. Check the response's resource URL and, when outcome is uncertain, read back before retrying to avoid duplicates. Do not treat an issue/PR title as an idempotency key.

## Actions, checks, releases, and guarded resources

Use `/actions/workflows` to list workflows, then read the workflow file from the repository at the relevant ref with the Contents API. Before dispatch, verify that `workflow_dispatch` is configured, inspect defined inputs, validate supplied names, types, choice values, and required fields against that workflow file (the current endpoint permits at most 25 input properties), resolve the exact branch or tag, and inspect referenced environment, publishing/deployment steps, repository documentation, and potential external cost. Do not assume a benign name means a benign workflow. `POST /actions/workflows/{workflow_id}/dispatches` takes `ref` and optional `inputs`; the current GitHub.com REST version documents a run ID and `html_url`, while older/Enterprise versions may return an empty success response. If no run ID is returned, correlate by workflow/ref/time before reporting a run. Rerun can repeat side effects; cancellation can disrupt a deployment. Classify each by effect. Jobs and logs can contain secrets or sensitive output; summarize only relevant fields. For run logs or artifact ZIPs, use the dedicated two-stage [`gh_actions_download` procedure](authentication-and-transport.md), which consumes the authenticated `302` privately and sends no Authorization header to the signed download URL. Inspect the archive in a private location and remove it afterward.

Checks and commit statuses are different APIs. Read both when determining CI state. Creating check runs is documented as a GitHub App operation; a PAT should use commit statuses when suitable and permitted. A combined status alone may not represent all check runs. Releases and tags are separate: a release can reference or create a tag, and publishing can trigger distribution or workflows, so inspect repository behavior before writing. Protect settings, rulesets, environments, deployments, collaborator/team access, secrets, visibility, and default branch are readable where authorized, but their mutations are intentionally outside routine version-one instructions and require exact user authorization and a fresh endpoint review. Deployment creation can emit events consumed by external systems.
