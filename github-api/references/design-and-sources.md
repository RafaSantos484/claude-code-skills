# Decision record and source trace

Decision date: 2026-09-27. The linked official GitHub pages were consulted for this implementation; API behavior must be rechecked at execution time for the chosen host, REST version, token type, and endpoint.

## Decision

**Selected:** a standalone `github-api` skill using direct REST and GraphQL HTTPS requests, with a transient-header `curl` pattern and no general `gh` dependency. This preserves the repository's environment-only credential rule while giving GitHub's permissions, Actions, Git objects, host layouts, and error model their own guidance. It does not alter the working GitLab skill. The direct-request approach costs more request and pagination guidance, but makes host, version, token selection, and response checks visible.

| Alternative | Disposition |
| --- | --- |
| Provider-neutral source-control skill | Deferred. Shared security principles are already in README; GitHub and GitLab differ enough in resources, permissions, versions, and content-writing paths that a common operating procedure would obscure important details and risk a GitLab regression. |
| General hybrid `gh` plus direct API | Rejected for this version. `gh` can use stored credentials and config; requiring proof of environment-only use for every command adds complexity and could silently change identity. `pr-review` retains its existing read-only `gh` flow independently. |
| Direct API guidance without a separate GitHub trigger | Rejected. A distinct trigger resolves ordinary resource tasks without broadening `pr-review` into a general GitHub mutation skill. |

**Boundary:** `pr-review` assesses code quality, correctness, and merge readiness using repository evidence. `github-api` reads and changes hosted GitHub resources: e.g. show PR files, post a requested review, approve a PR, create a PR, or dispatch a workflow. If a request combines assessment and posting, the assessment must meet `pr-review`'s evidence standard before an authorized external write. No `pr-review` change was necessary: its description already targets code review, and the new description excludes that purpose.

**Version one:** identity and repository checks; GitHub.com and version-aware Enterprise Server; repository/branch/tag/commit/content reads; single-file and atomic multi-file content writes; issues and comments; PR data, review requests, reviews, and guarded merge guidance; releases; Actions listing, logs/artifacts, dispatch/rerun/cancel with risk classification; checks and statuses; REST/GraphQL pagination and errors. Repository administration, collaborator/team changes, ruleset/protection/environment changes, secrets, deployment approvals, force refs, bulk mutation, GitHub App key lifecycle, packages, billing, Codespaces, and enterprise administration are not routine workflows. They need a fresh official-doc review and exact authorization. Projects v2 is documented as a GraphQL extension, not a full first-version procedure. No universal GHES compatibility claim is made.
